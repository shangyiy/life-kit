# /testing

The domain of testing. These principles and definitions hold for any entity under test (EUT): a function, a component, a whole system, a circuit, a device, or any process that turns inputs into outputs. Each kind of test applies them by choosing its EUT, where its oracle comes from, and which faults it models. They serve both to do testing work and to review it: to review, check the work against each principle in order and report each violation once, with the principle it breaks and the fix. The request decides what to produce.

## Principles, most important first

1. **Testing can reveal faults but never prove there are none.** A fault shows only if the faulty part is exercised, corrupts the state, and the corruption propagates to something a check observes, so testing gives false negatives. A passing run means these tests found nothing, not that nothing is wrong: never claim the EUT is fault-free, and don't treat testing as a substitute for reviews, analysis and other quality practices.
2. **Every test has an oracle that can fail.** The oracle gives a deterministic verdict by comparing actual with expected results: pass or fail, or, only where the spec itself grades quality, a grade on a scale fixed in advance. Expected results come from the specification and are decided before the run, never copied from the EUT's own output. The oracle checks every outcome the spec promises for the behavior, not only the easiest one to see. A test that cannot fail is useless: never write one without a check, and see each test fail once, by writing it before the EUT can pass it or by injecting a fault and restoring the EUT afterwards. Make an unfinished test fail on purpose; an expected-error test fails when the error does not occur. A case that cannot pass is just as useless: before judging any failure, show that each case can be passed, by a known-good reference that passes it; a case nothing can pass is a defect in the case, its oracle or its setup, not a finding about the EUT. The oracle can itself be wrong: validate it against known-good and known-bad cases before trusting its verdicts. Where the EUT can read or act on its surroundings, keep the oracle and its expected results out of its reach, so the EUT can neither observe nor change them.
3. **Behavior first.** Derive tests from the contract and the spec, not from the implementation: spec-based selection first, structure-based selection next; full structural coverage is a later aim, not the first one. A gap in the spec is a finding: report it, don't guess an expected result. Limit: spec-based tests cannot see behavior the spec never mentions, and structure-based tests cannot see missing function, so a suite needs both.
4. **One behavior per test: split by stimulus, never by check.** A behavior is one setup and one stimulus, the arrange and act steps, with all the outcomes of that stimulus. All checks on the outcomes of one stimulus stay in one test, however many results, fields or flags they inspect: one test per check repeats the arrange and act and adds no diagnosis, because the failing check already says which outcome is wrong. A test with a second setup or stimulus, such as a normal and an error case together, has a split personality and two reasons to fail: split it there. Each test has one diagnostic purpose, and its name states the behavior.
5. **Repeatable.** The same EUT under the same test gives the same verdict every run, alone or in any order: each test starts from a clean slate and leaves nothing behind for the next. Control in the fixture every source of variation the oracle does not judge: time, randomness, concurrency, shared state, the environment and external resources. **Randomness the test itself introduces,** in generated inputs or in a stand-in, is such a source, not a property of the EUT: fix or record the seed and the inputs it produced so any failure can be replayed exactly, and keep each failing input as a fixed test; reruns and pass rates never apply to it. Where completion can be observed, wait for it, not for a fixed time: a fixed wait is slow and still fails when the work takes longer or races. A wait the spec itself sets is part of the setup: fix it and record it. Record the setup a verdict depends on, so a run can be reproduced. A test that always fails beats one that fails now and then: a test that varies when the EUT does not is a test defect. **Retests follow a rule fixed in advance:** which results allow a retest, how many attempts at most, and how the attempts combine into one verdict, with every attempt recorded; retesting until a pass turns noise into passes and hides real faults. **Only when the EUT itself is not deterministic** does repeatability move to the verdict: run several independent trials, each from a clean state, state in advance whether a pass needs every trial or a share of them, and report the rate with the number of trials.
6. **Fast and actionable.** Slow tests are run less often, so feedback comes late: review and optimize sluggish tests, and replace expensive surroundings in the fixture. A failure says what broke, so the trace from failure to fault is short. Read each failure before acting on it: decide whether the fault is in the EUT, the test, the oracle or the setup.
7. **Partition the inputs and choose representatives.** Failing inputs are sparse and cluster in special cases, error conditions and boundaries, so a uniform sample rarely lands there, and ad hoc picks share the designer's wrong assumptions. Split the input space into blocks that are disjoint and complete, ideally uniform, and test a representative of each block and its boundaries. Be comprehensive without redundancy: happy paths, error paths, boundary cases at the limits of a type or resource, and corner cases that are unusual, interacting, pathological or hard to reproduce.
8. **Measure adequacy; don't assume it.** An **adequacy criterion** is a measurable condition the suite must meet: at spec level (each requirement, use case and scenario, basic and alternative flows; input-space combinations), at structure level (the parts of the EUT exercised), or by injected faults. **Coverage gauges thoroughness, not quality.** It says what ran, not whether an oracle checked it; what never ran is unknown. A measure is still better than none. Order: spec-based first, structure next, then injected faults to judge suite strength. Fix the criterion and the pass bar before the run, and name the criterion you claim and its weakness. A score from a sample of cases or trials is an estimate: report it with its sample size and uncertainty, and compare two versions on the same cases.
9. **Judge a suite by the faults it detects.** Inject small, realistic faults drawn from a fault model, one at a time, and count how many the suite detects. Faults planted in a program and defects modeled in a circuit, such as a line stuck at a fixed value, are the same idea, and the share detected (mutation score, fault coverage) is the same measure. It estimates the suite's power on real faults only as far as the injected faults represent them, and it rates the suite, not the EUT.
10. **Test early and often.** Defects cost more the later they are found. Grow the suite with each increment, rerun all of it on every change, and automate it so it stays repeatable, efficient and scalable. Each repaired fault gains a regression test.
11. **Thoroughness follows criticality; stopping is a judgment.** Parts whose failure would be costly, or that many others depend on, deserve the most thorough testing practicable. **When to stop:** coverage aims met, found-defect rate below target, cost of finding more defects above the expected loss, team consensus, or a decision to ship. Each is weak alone: a low found-defect rate can reflect weak tests as much as few faults; historical estimates hold only if past work is comparable; statistical models need a realistic input distribution and are hard in practice; coverage aims measure thoroughness, not absence of faults. In the end it is a judgment call: name the criterion you claim and its weakness.

12. **Results seen spend a test set.** Cases used to tune the EUT or the tests stop measuring anything beyond those cases: keep a held-out set apart from whoever tunes, judge with a judge independent of whoever built the EUT, and once its results are seen and acted on, report later results on it as tuning results.

## The six general principles

These are the main principles of verification and testing, applied by every technique:
- **Redundancy:** triangulate results with different techniques, at different levels and from different angles; inside one test or one technique, redundancy is waste.
- **Partitioning:** divide and conquer; test the subparts, then aggregate the results.
- **Approximation:** make the problem easier by simplifying the system or the testing task; whatever was simplified away is not tested by that test.
- **Visibility:** make information about the system accessible to tests, and its health visible to the team.
- **Feedback:** results must be actionable (principle 6).
- **Repeatability:** the same result every run (principle 5).

## Definitions

- **Fault, error, failure.** A fault (defect, bug) is the static root cause: a mistake, a wrong assumption, an incompatibility or a poor design decision. An error is the incorrect internal state the fault causes during operation; it is not directly observed. A failure is the deviation from expected behavior visible at the external interface, to a user or client. Classify a symptom by who observes it, not by who can find it: what only the builders see, such as a wrong internal state, a log or trace entry, repeated internal timeouts or retries, or what a probe on hidden state reveals, is an error, never a failure, even when a test detects it. Testing provokes failures (and, with extra visibility, errors); debugging traces them back to the fault.
- **Verification and validation.** Verification asks whether an artifact meets its specification ("built right"); validation asks whether it meets real needs ("right thing"). Both apply to intermediate artifacts as well as the final product. Static techniques judge an artifact without running it; dynamic ones, such as testing, run it.
- **Quality** is more than the absence of defects: fitness for stated and implied needs, judged by each stakeholder by their own needs. Engineer it by defining measurable characteristics. Reaching quality has costs, and so does missing it; it is not an afterthought, nor only testing. **What testing buys:** fewer faults and more confidence, plus scoped work, visible progress, diagnostic feedback, and documentation of behavior.
- **Contract:** what the EUT promises and what its user must do; implicit or explicit, informal or formal. An implicit contract still exists: make it explicit before testing. A precondition must hold for a use to be legal, a postcondition is what the EUT guarantees afterwards about results and state, and an invariant always holds. An EUT with state is specified by sequences: the state after several operations, operations that should cancel out, limit states such as empty or full, and operations the current state forbids. A limit the contract ignores is a gap: decide the behavior, give users a way to protect themselves, and test it.
- **Oracle:** the procedure that compares actual results with expected results and gives a verdict, pass or fail.
- **Test case:** a check with one diagnostic purpose, targeting one possible failure. A **suite** groups related cases and may mirror the structure of the EUT; no suite covers every behavior, so write one representative case per behavior of interest. An ideal suite finds every detectable fault early at minimum size; a real one finds some faults and has faults and redundancy of its own.
- **Fixture:** everything the test needs around the EUT. The **driver** applies the stimulus; collaborators present but not under test are real or replaced by **doubles**, stand-ins that belong to the fixture and are never the EUT. A test with a double assumes the collaborator's contract and does not test the collaborator; test that elsewhere and at higher levels.
- **Arrange, act, assert, then clean up:** set up, apply the stimulus, check, and restore. The assert step applies the oracle. Every test needs a design, selected inputs, an oracle, a fixture, and a measure of adequacy.
- **Levels:** unit, integration or component, system, acceptance; the whole team shares the job. Test functionality, quality attributes and regressions, and test unfamiliar third-party parts to learn how they behave.
- **Three dimensions** place any approach: level, input selection (ad hoc, random, systematic; exploratory testing uses tacit knowledge of the EUT), and intrusiveness (black, grey, white box).
- **Testability:** the effort to supply inputs, run the EUT, and check its outputs; it is part of maintainability. Efficiency is the cost of setting up and running; effectiveness is the cost of collecting outputs and deciding pass or fail (the oracle problem). Less testable designs mean more burden, fewer tests, more rework and lower quality.
- **Fault model:** the kinds of fault a suite is judged against. An injected fault is **detected** when at least one test fails on it.
